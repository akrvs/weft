# M2

Status: complete, live demo passed over the n0 network
Started: 2026-09-03

## Goal

Publish on one machine, fetch by hash on another, with no shared server
other than a relay you run. Records and blobs travel over iroh. The relay
is a cache with a contract: it stores what allowlisted authors push and
serves anything it holds to anyone.

## Decisions

| Topic | Decision |
|---|---|
| Discovery | Relay first. Clients hold a relay list. n0 public infrastructure for hole punching and endpoint discovery in M2 |
| Relay policy | Allowlist of author root keys. Everything else refused |
| Storage | redb for records and indexes, iroh-blobs FsStore for blobs |
| Blobs | Included. Relay pulls the blob from the pushing client, then confirms |
| Transport | iroh 1.1, custom ALPN `weft/relay/1`, one bidirectional stream per request |
| Framing | u32 big endian length, then canonical CBOR, 1 MiB cap |
| Blob hash | iroh-blobs Hash is plain blake3, identical to the record `blob` field |
| Crates | `weft-net` library, `weft-relay` binary, CLI gains network commands |
| Identity | Relay has its own iroh endpoint key, separate from Weft keys. Clients use ephemeral endpoint keys |

## Relay protocol

Requests and responses are CBOR maps with a `t` field naming the type.

| Request | Fields | Response |
|---|---|---|
| `put` | `records`: array of record bytes, at most 64 | `stored`: addresses, `rejected`: array of `{address, why}` |
| `get` | `address`: bytes(32) | `record`: bytes, or `missing` |
| `head` | `author`: bytes(32), `name`: text | `pointer`: bytes or absent, `manifest`: bytes or absent |

Rules the relay enforces on `put`:

1. Every record must parse and verify. Manifests in the batch are
   verified and applied before other records in the same batch.
2. `author` must be on the allowlist.
3. A record with a `blob` is stored only after the relay has downloaded
   the blob from the pushing client and iroh-blobs has verified the hash.
4. Pointers update the head index; manifests update the newest manifest
   index only when `seq` increases.

The relay never signs anything. Clients re-verify every record they
receive, including heads and manifests, against the protocol rules.

## Plan

1. `weft-net` crate. `wire` module: message types, framing, limits.
   `client` module: connect to a relay by endpoint id, put, get, head,
   blob push and fetch. `relay` module: iroh protocol handler, redb
   store, allowlist, blob download from the pusher.
2. `weft-relay` binary. `weft-relay init` creates the data directory and
   endpoint key. `weft-relay allow <address>` edits the allowlist.
   `weft-relay serve` prints its endpoint id and runs.
3. CLI. `weft relay add <endpoint-id>` and `weft relay list`.
   `weft push [address ...]` pushes all local records, or the named ones,
   to every configured relay, serving blobs while it runs. `weft fetch
   <address> [--out FILE]` gets a record and its blob, verifies, and
   stores locally. `weft resolve` gains `--relay` to ask for heads over
   the network. `weft sign` accepts files over the inline limit and
   emits a blob record.
4. Tests. In process relay and two clients over loopback. Allowlist
   rejection, invalid record rejection, blob round trip, head resolution
   with revocation.
5. Docs. `docs/relay.md` with the wire protocol. README gains the network
   flags. CI unchanged.

## Out of scope

DNS bridge, gateway, gossip, DHT, payments, personal store. Relay
quotas. Multiple relays coordinating. Mobile.

## Delivered

- `weft-net`: `wire` (framing, request and response types, limits),
  `client` (put, get, head, blob add and fetch), `relay` (protocol
  handler, allowlist, blob pull from the pusher), `index` (redb tables
  for records, heads, newest manifests).
- `weft-relay` binary: init, allow, deny, serve. Endpoint key at mode
  0600, allowlist as a text file of addresses.
- CLI: `relay add`, `relay list`, `push`, `fetch`, `resolve --relay`,
  and `sign` producing blob records for files over the inline limit.
- `docs/relay.md` wire protocol.
- Tests: two loopback integration tests with an in-process relay and two
  clients, covering allowlist refusal, unknown device refusal, head
  resolution with manifest, revocation propagation, and a 300 KB blob
  round trip. 19 tests in the workspace.
- Live demo over the real n0 infrastructure: relay behind NAT, push of
  five records including a 200 KB blob in about two seconds, resolve by
  author and name from a second home, fetch of page and blob, byte
  identical, local re-verification passes.

## Deviations from the plan

- Blob transfer is pull based. The relay downloads the blob from the
  pushing client over iroh-blobs after accepting the record, then
  confirms. iroh-blobs push requires provider side permission plumbing
  that added surface without benefit.
- The relay stores only the winning head per author and name rather
  than every pointer. Forks remain visible to clients that hold both,
  and the relay's job is to answer the head question.
- redb calls run inline on the async task. They are microseconds for
  this data size. Move to `spawn_blocking` when a relay holds enough to
  matter.
- Three unmaintained advisories are ignored in `deny.toml` with reasons.
  All are compile time or transitive through iroh with no runtime path.
