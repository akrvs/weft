# M25

Status: planned
Started: 2026-09-22

## Goal

Add the web of trust. A follow list is a reader's signed list of the
keys they vouch for, the same shape as petnames and labels. Walking
follows from the reader's own root gives each key a trust distance. The
browser shows the author's distance, lets the reader follow and unfollow,
and counts a labeler's hits only when the labeler is close enough. The
CLI edits follows and prints a distance with one shortest path.

## Decisions

| Topic | Decision |
|---|---|
| Record | `kind = "follow"`, body `{ follows: [ bytes(32) ] }`, 0 to 512 public keys sorted by bytes and unique. Head is the author's pointer `follows`. A whole snapshot, like `petname` and `label`. Grantable, not reserved |
| Endorsements | No second kind. An endorsement is a label on a key |
| Distance | 0 is the reader's root, 1 a key in the reader's list, then one per hop, at most 3. A key further out, or never reached, has no distance |
| Walk | Breadth first from the reader's root, lists read through `Resolver::list`, so each list is verified, authored by its key, and follows recovery redirects; a redirected key takes the distance of the key that named it. Lists are read in hop order, then key bytes order, at most `MAX_LISTS` 1024 of them. A list that fails to read or verify is skipped; only the reader's own list fails the walk |
| Pulls | An offline resolver walks the local store only; that is every page render. An online resolver pulls every list it reads; that is `weft trust --refresh`, the browser refresh button, and a follow |
| Labeler filter | `<home>/browser/reach`: `1`, `2`, `3`, or `any`, one line, default `2` when missing. A labeler counts only within reach. The Labels view shows each labeler's distance and whether it is in reach |
| Browser | The provenance panel shows `you`, `followed`, `2 hops`, `3 hops`, or nothing, and a follow or unfollow button. A Follows view lists, adds by key or petname, removes, imports, and refreshes. Writes are `put` then `point`, like petnames. The walk result is cached in the app for 60 s and dropped on every follow write and refresh |
| CLI | `weft follow add <key>`, `remove <key>`, `list [key]`, `import <key>`, through the M24 list writer; `add` pulls the new key's list. `weft trust [key] [--refresh]`: with a key, its distance and one shortest path; without, the count at each distance |
| Gateway, relays | Ignore follows. Relays store and serve them like any record |
| Dependencies | None new |

## Plan

1. Core: `follow.rs` with check, encode, decode, draft, `from_record`,
   sorted insert and remove, `contains`; `verify` arm; `follows.json`
   with valid records and one rejection per rule; protocol section 16.
2. Resolve: `Resolver::follows_of`, `Trust` with `distance` and `path`,
   `Resolver::trust(root)`; tests over a local store for the chain, the
   hop cap, the budget, a bad list skipped, a redirect, and a pull.
3. CLI: `follow` and `trust` commands; e2e over three identities.
4. Browser: reach file, view distance and follow state, labeler filter,
   Follows view, cache; drive smoke with a followed labeler in reach
   and an unfollowed one out of reach; screenshots.
5. Close.

## Out of scope

- Relays rate limiting by distance.
- Weighted or negative trust, distrust lists.
- Pulling lists during a page render.
- Follows in the gateway.
