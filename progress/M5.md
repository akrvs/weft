# M5

Status: complete, smoke tested on Linux with screenshots
Started: 2026-09-06

## Goal

The personal store becomes a gate. Grants are signed records that let an
application key read or write named kinds in the user's store, revocations
are signed records that end them, and a daemon over a Unix socket is the
only way an application reaches the store. The demo from the roadmap: an
application reads and writes through a grant, the user revokes it, the
next request fails.

## Decisions

| Topic | Decision |
|---|---|
| Grant record | `kind = "grant"`. Body: `app` bytes(32) application public key, `kinds` sorted unique array of 1 to 16 kind names, `access` uint 1 read, 2 write, 3 both, `expires` uint optional and after `created`. Reserved kinds `manifest`, `pointer`, `grant`, `revoke` cannot be granted. Root or device signed |
| Revocation | `kind = "revoke"`. Body: `grant` bytes(32) address of the grant record, also listed in `refs`. Root or device signed. A grant is active when it verifies, is not expired, and no verifying revoke by the same author cites it |
| Verification | `verify` parses grant and revoke bodies the way it parses manifests and pointers, so a malformed grant never verifies anywhere |
| Gate transport | New binary `weft-store` listening on `<home>/store.sock`, mode 0600. Length framed canonical CBOR as in `docs/relay.md`, one request and one response per frame, many in sequence per connection |
| Application auth | The daemon sends `hello { nonce }` on connect. The client answers `auth { app, sig }` with `sig` over `"weft/store/1" || 0x00 || nonce`. Every later request is checked against the grants active at that moment, so a revoke bites on the next request of an open connection |
| Requests | `list { kind }` returns addresses of the user's verified records of that kind. `get { address }` returns a record whose kind is readable. `put { kind, body, refs }` has the daemon sign a record as the user with its device key and store it |
| Write semantics | `weft-store serve --device <label>` unlocks one device key at start with `WEFT_PASSPHRASE` or a prompt and holds it zeroized in memory. Every put is verified against the local manifest before it is stored |
| Scope of reads | Only records whose author is the store's root. Fetched records by others are not the user's log |
| Sample app | `weft-app` in the same crate: `key` makes an encrypted app key, `read <kind>` lists and prints, `write <kind> <file>` puts. Passphrase from `WEFT_APP_PASSPHRASE` or a prompt |
| CLI | `weft grant add <app> --kind k --read --write --expires --as`, `weft grant list`, `weft grant revoke <grant> --as`. `weft inspect` prints grant and revoke bodies |
| Browser | A store button opens a view listing the user's kinds with counts and the active grants, each with a revoke form taking device and passphrase. The browser still reads the home directory directly; moving it behind the daemon is later |
| Dependencies | tokio gains `net` and `io-util` for Unix sockets and framed reads. No new crates |

## Layout

```
crates/core/src/grant.rs      Grant, Revoke, encode, decode, from_record
crates/home/src/store.rs      Store::grants, active grants over a record set
crates/store/                 weft-store
  src/lib.rs                  exports
  src/error.rs                typed Error
  src/wire.rs                 Hello, Auth, Request, Response, framing over a stream
  src/gate.rs                 Gate: the one authorization choke point
  src/server.rs               listener, handshake, request loop
  src/client.rs               Client used by weft-app and tests
  src/bin/weft-store.rs       serve
  src/bin/weft-app.rs         key, read, write
  tests/gate.rs               end to end over a real socket in a temp home
docs/protocol.md              section 10 Grants, section 9 updated
docs/store.md                 store wire protocol
vectors/grants.json           grant and revoke fixtures
```

## Plan

1. `weft-core`: `grant.rs` with `Grant` and `Revoke`, checks for every
   rule, `verify` extended, fixtures in `vectors/grants.json` with a
   negative entry for every rejection, `records` vector test reused.
2. `weft-home`: `Store::grants` returning active grants for an author at a
   time, tests for revoke and expiry.
3. `docs/protocol.md` section 10 and `docs/store.md`.
4. `weft-store`: wire with negative decode tests, `Gate`, server, client,
   the two binaries. Integration test: no auth refused, bad signature
   refused, no grant refused, read grant lists and gets, write grant puts
   and the record verifies, reserved kind refused, expired grant refused,
   revoke ends access on the same connection.
5. CLI grant commands and inspect.
6. Browser store view and revoke command.
7. Smoke test: daemon, app writing a note and reading it back, revoke from
   the browser, app refused. Screenshot the store view.

## Out of scope

Browser behind the daemon, grants for records by other authors, grant
delegation, app identity display names, relay replication of grants
beyond the existing push, DHT, payments, challenge response login for
sites.

## Delivered

- `weft-core`: `Grant` and `Revoke` with a check for every rule, `verify`
  parses both kinds so a malformed grant never verifies, `sign_in` and
  `verify_in` for domain separated signatures outside records, sixteen
  fixtures in `vectors/grants.json` with a rejection named for every rule.
- `weft-home`: `Store::grants` returns the grants active for an author at
  a time, valid, unexpired, and not cited by a valid revoke.
- `weft-store`: the gate over a 0600 Unix socket. Nonce handshake, one
  authorization choke point in `Gate::allow` consulted on every request,
  reads limited to the root's verified records, writes signed by the
  daemon's device key and verified against the local manifest before they
  are stored, reserved kinds refused, 1 MiB frames, 60 second idle close.
  Binaries `weft-store serve --device` and `weft-app key | whoami | read |
  write`, the app key encrypted with the home keystore format under
  `WEFT_APP_PASSPHRASE`.
- CLI: `weft grant add | list | revoke`, `weft inspect` prints grant and
  revoke bodies.
- Browser: a store button opens a dialog with the user's kinds and counts
  and the active grants, each with a revoke form.
- Docs: `protocol.md` section 10 and `docs/store.md`.
- 46 tests in the workspace, 6 new.
- Smoke test with release binaries in a scratch home: init, device,
  manifest, daemon, app key, `weft-app read` refused before a grant,
  grant with read and write, `weft-app write` then `read` returns the
  note, revoke from the browser's store view with the root passphrase,
  `weft-app read` and `write` refused, `weft grant list` empty, the revoke
  record inspects with the grant in `refs`. Screenshots of the store view
  before and after the revoke.

## Deviations from the plan

- `Gate::new` takes the root public key alongside the home so tests can
  build a gate without Argon2id key files. The daemon passes
  `home.root()`.
- `weft-app` gained `whoami` so the demo can read the app address without
  regenerating the key.
- The daemon handles SIGTERM as well as SIGINT and removes its socket on
  both. A stale socket from a hard kill is removed at the next start
  after a failed connect.
- The browser store view lists reserved kinds in the counts too, since
  they are the user's records. Only the gate hides them from applications.

## Open for M6

- The browser reads the home directory directly. Moving it behind the
  daemon makes the store the single gate the design asks for.
- The store re-reads and re-verifies every record per request. Fine at
  hundreds of records, needs an index before thousands.
- `weft-app` holds its key in the home keystore format but the daemon has
  no notion of application identity beyond the key address. Display
  names, and the challenge response the handshake already uses, belong to
  M6 login.
- Grants only cover records by the store's root. Fetched records by others
  are invisible to applications.
