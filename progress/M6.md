# M6

Status: complete, smoke tested on Linux with screenshots
Started: 2026-09-06

## Goal

Log in with no account and no password. A service issues a challenge
naming itself and a nonce, the user's device signs it as a record of kind
`login`, the service verifies the record against the user's manifest and
opens a session for the root address. The demo from the roadmap: the
gateway's login page, signed from the browser's consent dialog or from
the command line, ends with "logged in as" the user's root address.

## Decisions

| Topic | Decision |
|---|---|
| Response format | A record of kind `login`, verified by the one `verify`. Body is the challenge verbatim: `service` text, `nonce` bytes(32), `expires` uint greater than `created`. `refs` empty. Never stored, never relayed: `Store::put` and the relay refuse the kind |
| Challenge | Canonical CBOR map of the same three fields, carried as lowercase base64url without padding in `weft:login?c=<text>` links and on the command line |
| Proof | Canonical CBOR map `login` bytes(record) and optional `manifest` bytes(record), at most 64 KiB, same text encoding. The manifest is required when the login is device signed and must be the author's own root signed manifest |
| Service binding | `service` is the verifier's origin, 1 to 253 bytes of visible ASCII with no uppercase, matched exactly. The gateway derives it from its bind as `http://host:port` unless `--origin` says otherwise |
| Freshness | The verifier checks the inline manifest offline. A verifier with relays fetches the manifest head and verifies against whichever manifest has the highest `seq`. A failed fetch falls back to the inline manifest |
| Signer | The store daemon answers `login { challenge }` for an application holding an active grant covering kind `login` with write access, signs with its device key, never stores the record. `login` is grantable, not reserved. The browser and `weft login sign` sign from the keystore directly |
| Gateway | GET `/login` opens a pending challenge and redirects to `/login/<nonce>`, which shows the `weft:login` link, the challenge text, a paste form, and refreshes every three seconds without script. POST `/login` takes a proof as `text/plain` or form field `p`, verifies, marks the nonce satisfied, sets the session cookie. POST `/logout` ends it. GET and HEAD stay the only methods elsewhere |
| Sessions | In memory. Pending challenges live five minutes, sessions one day, each capped at 1024 with expired entries swept on insert. Cookie `weft_session`, 32 random bytes, `HttpOnly`, `SameSite=Strict`, `Secure` when the origin is https |
| Browser | `weft:login?c=` in the address bar or a clicked link opens a dialog naming the service, expiry, device, and passphrase. On confirm the browser signs from the keystore, builds the proof with the local manifest, and POSTs it to `<service>/login` over reqwest. Only https origins and loopback http are accepted |
| CLI | `weft login challenge --service`, `weft login sign <challenge> --as`, `weft login verify <proof> --service`. `weft inspect` prints login bodies |
| Dependencies | reqwest 0.13 already in the tree through iroh, default features off with `rustls`, used by the browser only. No other new crates |

## Plan

1. `weft-core`: `login.rs` with `Challenge` and `Proof`, checks for every
   rule, `verify` extended, `Error::Login`, fixtures in `vectors/login.json`
   with a negative entry for every rejection, vector test.
2. `weft-home` and `weft-net`: refuse to store or relay `login` records,
   tests for both.
3. `docs/protocol.md` section 12, section 9, `docs/store.md`.
4. `weft-store`: `login` request and response with negative decode tests,
   `Gate::login`, client, `weft-app login`. Integration test: no grant
   refused, read only grant refused, write grant signs a proof that
   verifies, nothing stored.
5. `weft-resolve`: `freshest_manifest`.
6. `weft-gateway`: `login.rs`, routes, pages, tests over a real listener:
   redirect, challenge page, bad proof refused, wrong service refused,
   expired nonce refused, good proof sets the cookie, second use of the
   nonce refused, logout clears.
7. CLI `weft login` and inspect, end to end test in `cli/tests/e2e.rs`.
8. Browser dialog and POST.
9. Smoke test with release binaries: gateway, `weft login sign` pasted into
   the form, then the browser dialog path. Screenshots of the dialog and
   the logged in page.

## Out of scope

Selective disclosure proofs, service identities, session persistence
across gateway restarts, pages that read the session, login through the
`weft-browser` web view for arbitrary https sites, social recovery,
payments.

## Delivered

- `weft-core`: `login.rs` with `Challenge`, `Proof`, and `Login`, a check
  for every rule, `verify` parses login bodies, `Error::Login`, base64url
  text helpers, twenty six fixtures in `vectors/login.json` covering
  records, challenges, and proofs.
- `weft-home`: `Store::put` refuses login records, `Store::manifest_record`
  returns the newest manifest record.
- `weft-net`: the relay refuses login records.
- `weft-resolve`: `Resolver::freshest_manifest` takes the highest `seq`
  among the local store and every relay head.
- `weft-store`: `login { challenge }` request answered with a proof for an
  application holding a write grant on kind `login`, `weft-app login`.
- `weft-gateway`: `Gateway` over a `Resolver` and `Logins`, `--origin`,
  GET `/login` redirecting to `/login/<nonce>`, a script free challenge page
  that refreshes every three seconds, POST `/login` for `text/plain` or a
  form field, POST `/logout`, in memory pending and session tables capped
  at 1024 with sweeping, `HttpOnly` `SameSite=Strict` cookies.
- CLI: `weft login challenge | sign | verify`, `weft inspect` prints login
  bodies.
- Browser: `weft:login?c=` opens a consent dialog naming the service,
  expiry, and challenge. On confirm the browser signs from the keystore and
  POSTs the proof over reqwest to https or loopback http.
- Docs: `protocol.md` section 11 and section 9, `docs/store.md`.
- 55 tests in the workspace, 9 new.
- Smoke test with release binaries in a scratch home: gateway on 8090,
  challenge page fetched with curl, `weft login sign --as laptop` pasted
  through POST, logged in as the root, replay refused, waiting tab claimed

  dialog and the result.

## Deviations from the plan

- No new crate. `Challenge` and `Proof` live in `weft-core` and the
  session table in `weft-gateway`, so a verifier needs only the core.
- `reqwest` with `rustls-no-provider` panics at client build when no
  provider is installed. The browser depends on `rustls` with `ring` and
  installs it at start. Found by the smoke test, not by the tests.
- The gateway's frozen "GET and HEAD only" gains two POST routes, `/login`
  and `/logout`. Everything else still answers 405.
- A stranger with no manifest is a valid identity to the gateway. The
  demo shows who signed, it does not decide who is allowed in.

## Open for M7

- The session cookie is a bearer token in memory. A gateway restart logs
  everyone out. Persisting sessions or signing them is a later choice.
- The waiting tab polls with a meta refresh every three seconds. A page
  that must stay script free has no other option.
- `weft-browser` is not registered as the OS handler for `weft:` links, so
  a challenge page in Firefox needs the link pasted into the browser.
- The browser still signs from the keystore directly rather than through
  the store daemon.
